# OneAPI browser error monitoring

This change adds browser error capture only to https://oneapi.laisky.com. It does not change Go/OpenTelemetry telemetry, its attribute allowlists, release workflows, or production rollout controls. SDK 11.7.0 supports the shipped React 18 and 19 themes. There are no configured project identifiers, real DSNs, upload credentials, test events, or server-side Sentry instrumentation.

## Supported themes and disabled behavior

The checkout contains Modern, Berry and Air packages, which Docker builds sequentially. Although AGENTS.md still mentions Default, `common/config/config.go` lists only these three valid themes; `main.go:isThemeValid` redirects `THEME=default` to Modern for compatibility. Default therefore uses the same Modern integration, not a separate obsolete entry point.

All three entry points initialize the same shared policy before React mounts. Modern additionally uses React 19 root error hooks; the shared reporting boundary covers render failures in React 18 and 19. All routers use declarative BrowserRouter/Routes; there is no independent data-router errorElement that bypasses the root boundary. GlobalHandlers covers uncaught errors and unhandled rejected promises. Reports of the same exception object are deduplicated. Enabled boundary failure renders a blank root, matching the previous root-crash outcome; no new user-facing fallback text is introduced.

Without all validated settings, or on a different hostname/protocol/port, the reporter stays disabled, adds no root callbacks, and uses a transparent wrapper. SDK initialization/capture/transport failures cannot throw into application code; diagnostics use fixed strings only. Partially initialized handlers cannot send because the final transport is gated on successful client initialization.

## One public runtime configuration: separate approval gate

A project owner must separately approve/create the correct OneAPI JavaScript project and its public DSN. Do not reuse the blog project's settings. No project, key, token or access grant is created by this PR. The last authorized project inventory found no OneAPI project; recheck that prerequisite through approved account access before activation.

The root-admin System Settings screen exposes one atomic `BrowserSentryConfig` option, also available through the existing protected `PUT /api/option/` API for all supported themes. Its value is JSON with exactly two fields: `dsn` and `environment`. `dsn` must be the approved HTTPS public Sentry ingest DSN with a 32-character lowercase hexadecimal public key and numeric project path; passwords, port overrides, query/fragment, foreign hosts and extra fields are rejected. `environment` is `production`, `staging`, or `development`. Empty/whitespace clears the setting and disables the next page load. A valid supplied setting activates automatically; there is no separate enabled flag. Never enter auth tokens, upload credentials, application secrets or a release override. Validation and normalization run before persistence in both the API handler and direct model writes. Invalid historical database values safely project to disabled.

`GET /api/browser-config` is an anonymous, no-store endpoint returning only the validated typed public Sentry setting (or null). It never returns the option map, status cache, request/session data, credentials or release identifiers. Each target page fetches it once with credentials omitted, no referrer, no redirects, same-origin delivery and a 2048-byte response limit. The configuration request waits at most one second. Only after valid configuration arrives does the page load the named-export SDK bridge, with a separate one-second deadline (at most two seconds total before rendering); absent/invalid settings and unsupported hosts never download or evaluate the SDK. SDK import throw/rejection, missing exports or a load timeout remain disabled and cannot initialize from a late module. Missing/invalid configuration, HTTP/network failure, unavailable streaming/fetch APIs, malformed/oversized data or a load timeout continue with normal disabled application behavior. Early module-evaluation errors before configuration readiness are unavailable to the reporter; no errors are buffered or replayed. Original application imports remain in place. A shared terminal owner redispatches an unexpected mount rejection through the native browser error path exactly once, including when reporting is disabled; rendering is never retried automatically. SDK initialization failures remain disabled and cannot send partially registered events. The initial request and reporter are idempotent per window; no background polling, automatic retries or SDK retargeting occurs.

After a successful settings update, reload each browser page to apply it. Existing pages retain their frozen configuration until reload, including after a clear. Public DSN/environment changes require no frontend rebuild or container restart. Replicated instances follow the existing runtime-option synchronization interval, so allow that propagation before reloading. A rollout still requires a separately reviewed code deployment before this runtime endpoint/bootstrap exists. This task does not modify an actual setting, project, security policy, credential or deployment.

## Immutable browser release identity

Vite embeds a build-only `one-api-{theme}@sha256:<64 lowercase hex>` release identity. This is a SHA256 identity of enumerated frontend source/build inputs, dependency locks, compiler runtime version/platform/architecture and explicit build-affecting public values; it is not a Git SHA and cannot be supplied through runtime configuration. The generated `web/legacy/browser-release-inputs.json` allowlist enumerates theme source/public assets, index, Vite/compiler/CSS configuration, package/lock files and shared Sentry/build helpers. The build reads no Git metadata, .env files, private instructions, arbitrary ignored files, dependency trees or generated artifacts for this identity, so it works in Docker without `.git`. A build guard checks the entire source/public input list (including Tailwind content and Sass partials), rejects unlisted actual resolved first-party modules before loading, rejects symbolic links, and rechecks the same immutable input-byte snapshot before writing artifacts; when adding/removing relevant source/config inputs, update and review the generated allowlist. Runtime setting changes leave release identity unchanged. Record the source-qualified Git SHA and each emitted build release together in deployment evidence; matching build inputs/runtime are required to reproduce an identity.

There are no public Sentry Docker build arguments or `VITE_SENTRY_*` configuration fields. No `SENTRY_AUTH_TOKEN` belongs in browser variables, Docker build arguments, files copied into images, JavaScript, Git, logs or public artifacts. No release workflow or production setting is changed here.

## Privacy and diagnostic limits

The SDK uses no default integrations, only GlobalHandlers. It has no tracing sampler or tracing/replay/network/console integrations, zero breadcrumbs, explicit disabled dataCollection categories, and log/metric/transaction drop guards. The final envelope transport permits only a projected error event, with minimal headers; it drops attachments, sessions, logs, metrics, traces, replays and client reports, including internal SDK errors that bypass beforeSend. Fetch uses credentials:omit and referrerPolicy:no-referrer.

Projection retains only bounded known exception categories, a fixed redacted error value, validated deployment identifiers, fixed site/theme tags, event identity/time, and up to 3 exceptions with up to 30 static stack locations each. It discards all arbitrary messages, user metadata, request URLs/headers/cookies/bodies, extra/context/tags/fingerprints, breadcrumbs, source lines, frame variables and function names. This excludes API keys, auth tokens, prompts, completions, chat history, local-storage secrets and MCP tool arguments/results.

Static frame filenames must be HTTPS first-party assets, have a known generated filename shape, and exactly match an immutable snapshot of at most 40 module/script/preload asset URLs loaded at initialization. Queries/fragments are removed; credentials and unsafe source/third-party paths are rejected. Later lazy-loaded chunks are deliberately omitted from stack diagnostics unless already preloaded. Exception text and component stacks are never sent. These constraints reduce issue detail/grouping; changing the allowlist requires privacy tests and review.

Network ingestion necessarily exposes the connection IP to the receiving service. Before any real event, the project owner must approve and verify effective OneAPI project IP/PII handling, retention, access control and server-side scrubbing. Preventing IP storage alone is insufficient: Sentry still derives geographic data from the connection IP. Require the approved project-level Advanced Data Scrubbing rule `[Remove] [Anything] from [$user.geo.**]` before ingestion, and verify that no user geo fields survive. See [Sentry's server-side scrubbing guidance](https://docs.sentry.io/security-legal-pii/scrubbing/server-side-scrubbing/#geographic-information), checked 2026-10-13. Do not change organization-wide or blog settings; any such change requires separate authorization. Browser code does not set user identity/IP and cannot enforce collector-side policy.

## Private source maps and release correlation: separate approval gate

Production builds currently generate no source maps by default. Do not turn on legacy GENERATE_SOURCEMAP for a publicly shipped build without a reviewed private upload-and-exclusion pipeline. Hidden source maps suppress the bundle link; they do not prevent public map access.

Before a source-map rollout, separately review a private build step using each exact embedded theme release identity and identical artifact bytes for the corresponding theme output. Generate maps only in that private staging area. Use a least-privilege upload token supplied by the approved secret store to the private upload process; never put it in build arguments or browser configuration. Use classic release plus exact retained HTTPS asset filename correlation for the approved OneAPI project. The privacy projection deliberately drops debug_meta and frame debug_id, so DebugID pairing is unsupported without a future reviewed policy extension. Upload matching private artifacts using this classic release/URL correlation, then delete/exclude every *.map before Docker copies web/build or any static artifact is published. Fail packaging if any map remains, verify no embedded sourceMappingURL/data-URL map is present, and deny *.map at the public serving layer as defense in depth. Keep maps/source artifacts private under an approved retention policy.

Do not run an upload, credential command, production build publication or synthetic real telemetry event as part of this task. A real event may be approved only after the intended project/configuration and privacy prerequisites exist. First use mocked transport tests; an approved staged smoke check must inspect the received redacted event and release correlation without user data.
