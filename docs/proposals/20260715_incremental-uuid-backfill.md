# Proposal: Incremental External UUID Backfill Remediation

- Status: Proposed; required before the current UUID migration is finalized
- Date: 2026-07-15
- Area: model initialization, data migration, UUID indexes, split log database
- Related: [GitHub issue #354](https://github.com/Laisky/one-api/issues/354),
  [External UUIDv7 Resource Identifiers](./20260703_external-uuid-identifiers.md)

## 1. Summary

The external UUID project adds stable UUIDv7 identifiers to 12 resource tables
and denormalized UUID copies for 15 integer references. New writers generate
owned UUIDs and populate FK UUIDs, but rows created before that deployment still
need a one-time backfill.

The reviewed implementation has the right scalability foundation: it reads
missing target rows in batches, resolves only references used by each batch,
performs conditional updates, promotes owned UUID indexes to unique indexes,
and records completion in data_migrations. It is not yet safe to finalize.

The highest-severity defect is split-database ordering. The current coordinator
runs log reconciliation before primary owners receive UUIDs. Log validation can
therefore classify a missing log FK UUID as unresolvable, write the v2 log
completion marker, and permanently skip that row after the primary UUID becomes
available. The remediation in this proposal replaces the v2 marker generation,
makes one topology-aware coordinator the sole completion authority, and
validates both databases as one dependency graph before writing either marker.

This document supersedes only the migration mechanics in the parent external
UUID proposal. It does not change the API identifier contract, UUIDv7 format,
integer primary keys, or the per-resource API rollout.

## 2. Background and Current State

### 2.1 Domain context

Integer IDs remain the internal primary and foreign keys. Canonical hyphenated
UUIDv7 strings are the external identifiers. Denormalized FK UUID columns avoid
cross-database joins and response-time fan-out, especially for logs stored in a
separate LOG_DB.

Owned UUIDs are generated by model create hooks. FK UUIDs must be copied from
the referenced resource by each write path because a generic create hook cannot
resolve every owner without additional database reads. During a rolling
upgrade, old writers and stale cached objects can still insert rows with missing
UUID values, so completion requires a writer-compatibility barrier rather than
only a successful backfill pass.

### 2.2 Existing implementation to preserve

The reviewed branch state provides:

- a data_migrations table with UTC completion timestamps;
- separate completion keys for primary and split-log roles;
- owned-UUID and FK-UUID batch readers;
- batch-local ID and token-name reference resolution;
- separate indexed passes for NULL and empty-string values;
- conditional updates that recheck observed references;
- orphan-tolerant keyset scans;
- explicit owned UUID unique-index promotion; and
- SQLite, split-database, marker, concurrency, dialect, and scale test
  foundations.

The remediation should preserve those useful pieces where they satisfy the
invariants below. It should not reintroduce full-table reference maps, durable
per-row migration state, or a general distributed migration framework.

Before implementation, record the baseline commit containing
model/data_migration.go, the v2 marker implementation, and the batch-local
resolver files. If the target branch does not contain that commit, land the
reviewed patch as a prerequisite or implement its foundations together with
this remediation; do not assume unstated worktree state.

### 2.3 Review findings that require remediation

| Priority | Finding | Consequence | Required correction |
| --- | --- | --- | --- |
| P0 | Split log reconciliation runs before primary owned UUID backfill | A v2 log marker can be written while log FK UUIDs will become fillable later | Reorder phases and make completion a global coordinator decision |
| P0 | Existing v2 markers may already represent false completion | Corrected code could continue skipping incomplete data | Introduce v3 keys and ignore v2 for completion |
| P0 | Unified or split topology is inferred from gorm.DB pointer equality | Cloned or wrapped handles can select the wrong path | Construct explicit topology during database initialization |
| P0 | The primary target registry always includes logs | A stale primary logs table can be scanned or mutated in split mode | Give authoritative log ownership exclusively to LOG_DB |
| P0 | Migration execution moved from InitDB to InitLogDB | InitDB-only callers silently lose primary catch-up behavior | Preserve a marker-free compatibility path and add one bootstrap orchestrator |
| P1 | A fixed 200-row conditional update can exceed SQLite's portable bind limit | One-FK updates use about 1,000 binds and token updates about 1,400 | Calculate chunk size from a 900-bind budget |
| P1 | Token-name keys are bounded but all duplicate matches can be returned | One ambiguous key can still materialize O(table) token rows | Aggregate per requested key and return at most one result per key |
| P1 | Unique-index DDL runs in ordinary startup | Large tables can block readiness or wait indefinitely for locks | Move promotion to finalizer mode with dialect-specific online DDL |
| P1 | The scale test checks final rows but not query or heap bounds | A regression can pass while rematerializing large tables | Instrument query counts, row counts, binds, plans, locks, and heap |

## 3. Goals and Non-Goals

### 3.1 Goals

1. Backfill all resolvable owned and denormalized UUIDs without overwriting
   populated values.
2. Bound application memory, query result size, bind count, and write size by
   configured batch limits rather than table cardinality.
3. Support SQLite, MySQL, and PostgreSQL in unified and split-log topologies.
4. Resume safely after cancellation, process failure, database failure, or a
   concurrent migration worker.
5. Permit permanent orphans and ambiguous historical token names without
   blocking unrelated rows.
6. Write completion markers only after the UUID-aware-writer barrier, global
   reconciliation, required index promotion, and final validation.
7. Make a completed coordinator invocation perform only one marker lookup in
   unified mode or two marker lookups in split mode.
8. Preserve existing InitDB callers while giving the application one supported
   completion-capable bootstrap path.

### 3.2 Non-goals

- Replacing integer primary keys or internal integer foreign keys.
- Changing the external canonical hyphenated UUIDv7 representation.
- Changing API request or response rollout rules from the parent proposal.
- Building a reusable job scheduler, lease system, durable cursor, or row-level
  pending ledger.
- Inventing UUIDs for deleted owners or choosing among ambiguous token-name
  matches.
- Automatically repairing populated malformed UUIDs or mismatched denormalized
  UUIDs; finalization reports and blocks on those cases.
- Converting CHAR(36) UUID storage to native or 16-byte storage.
- Automatically accepting a LOG_DB repoint as completed migration state.

## 4. Terminology and Invariants

| Term | Meaning |
| --- | --- |
| Owned UUID | The UUID identifying the row itself, such as users.uuid |
| FK UUID | A denormalized UUID copied from the row referenced by an integer FK |
| Fillable gap | A missing FK UUID whose current referenced row has a populated UUID |
| Orphan | A historical integer FK whose referenced row no longer exists |
| Ambiguous token key | A (user_id, token_name) pair matching more than one populated token |
| Catch-up mode | Marker-free, restartable reconciliation allowed during mixed-writer rollout |
| Finalizer mode | Synchronous reconciliation after all UUID-unaware writers are drained |
| Completion marker | A versioned row proving one database role passed the current finalization contract |

All implementation work must preserve these invariants:

1. A populated owned UUID is immutable.
2. A populated FK UUID is never silently overwritten by catch-up.
3. An FK UUID update rechecks the integer FK observed during the candidate read.
4. A token UUID update rechecks id, user_id, and token_name.
5. Missing owned UUIDs are always fillable and must be zero at finalization.
6. Missing FK UUIDs may remain only for absent references, permanent orphans, or
   ambiguous historical token names.
7. A populated FK UUID that disagrees with its live owner blocks finalization.
8. A malformed or duplicate populated owned UUID blocks finalization and
   requires explicit operator remediation.
9. A failed or cancelled phase writes no completion marker.
10. Existing v2 markers never suppress v3 reconciliation.
11. In split mode, LOG_DB is the only authoritative owner of logs and their
    indexes; a logs table on the primary database is ignored.
12. Business helpers return wrapped errors; the bootstrap boundary logs each
    terminal error once.

## 5. Data Ownership and Topology

### 5.1 Owned UUID tables

The 12 owned UUID tables are users, tokens, channels, redemptions, logs,
token_transactions, user_request_costs, traces, async_task_bindings,
mcp_servers, mcp_tools, and passkey_credentials.

In unified mode, the primary database owns all 12. In split mode, the primary
database owns the 11 non-log tables and LOG_DB exclusively owns logs.
No split-mode phase may migrate, scan, validate, or change indexes on a stale
logs table in the primary database.

### 5.2 Denormalized reference ownership

| Target role | Target columns | Reference source |
| --- | --- | --- |
| Primary local | users.inviter_uuid; tokens.user_uuid; redemptions.user_uuid | Primary users |
| Primary local | token_transactions.token_uuid and user_uuid | Primary tokens and users |
| Primary local | user_request_costs.user_uuid | Primary users |
| Primary local | async_task_bindings.user_uuid, token_uuid, channel_uuid | Primary users, tokens, channels |
| Primary local | mcp_tools.server_uuid; passkey_credentials.user_uuid | Primary mcp_servers and users |
| Unified logs | logs.user_uuid, channel_uuid, token_uuid | Primary users, channels, tokens |
| Unified transactions | token_transactions.log_uuid | Primary logs |
| Split logs | LOG_DB.logs.user_uuid, channel_uuid, token_uuid | Primary users, channels, tokens |
| Split transactions | Primary token_transactions.log_uuid | LOG_DB.logs |

### 5.3 Explicit topology

Database initialization must construct a topology value and pass it through the
migration call chain. Unified mode is selected by the unified initialization
path where LOG_DB is assigned to DB. Split mode is selected by the dedicated
log-database configuration path. Migration code must not rediscover topology by
comparing gorm.DB pointers.

Conceptually, the value contains:

    primary: initialized primary database handle
    log: initialized authoritative log database handle
    mode: unified or split

A session clone or instrumentation wrapper must not change the selected mode.
When a dedicated log DSN is configured, the deployment is treated as split even
if an operator points both DSNs at the same physical server.

## 6. Target Implementation

### 6.1 Coordinator and modes

RunExternalUUIDMigrations becomes a thin public entry point over one
topology-aware coordinator. The coordinator accepts a typed catch-up or
finalizer mode. Primary and log helpers perform idempotent phases but cannot
write markers independently.

Keep compatibility globals at the model boundary, but do not read DB, LOG_DB,
or the finalizer environment variable inside phase helpers. Use these internal
contracts:

    type externalUUIDTopology struct {
        primary *gorm.DB
        log     *gorm.DB
        mode    externalUUIDTopologyMode
    }

    func runExternalUUIDMigrations(
        ctx context.Context,
        topology externalUUIDTopology,
        mode externalUUIDMigrationMode,
    ) error

RunExternalUUIDMigrations(ctx) reads the already initialized topology and typed
mode, then delegates. InitDatabases(ctx) owns handle initialization and stores
the topology. Tests call the internal coordinator with injected handles instead
of mutating topology globals.

At entry:

1. Validate mode, non-nil handles, and topology without issuing metadata queries.
2. Read the current-generation marker for each applicable role.
3. Return immediately only when every applicable marker exists.
4. If any marker is absent, validate required schema and run the complete
   topology-specific phase sequence.
5. In catch-up mode, stop without unique-index promotion or marker writes.
6. In finalizer mode, promote indexes, run global validation, and write markers.

The new keys are:

- external_uuid_backfill_v3_primary; and
- external_uuid_backfill_v3_log for split mode only.

The v2 rows remain historical records but have no completion authority.
The marker-only claim applies to the UUID coordinator after normal additive
schema initialization; it does not claim that the application's separate
AutoMigrate phase performs no metadata queries.

| Topology and marker state | Required action |
| --- | --- |
| Unified: v3 primary exists | Return after the primary marker lookup |
| Unified: absent or v2 only | Reconcile; finalizer writes v3 primary |
| Split: both v3 markers exist | Return after both marker lookups |
| Split: neither exists or v2 only | Reconcile; finalizer writes log then primary |
| Split: log only | Reconcile and validate globally; preserve log timestamp and write primary |
| Split: primary only | Treat as inconsistent recovery; reconcile and validate globally, preserve primary timestamp, write log, and emit a warning |

Primary-only recovery is the sole exception to normal primary-last insertion.
It repairs a crash, manual deletion, or earlier defect; it never rewrites the
existing primary marker timestamp.

### 6.2 Phase ordering

| Phase | Unified database | Split databases |
| --- | --- | --- |
| 1 | Backfill all owned UUIDs | Backfill primary owned UUIDs, excluding logs |
| 2 | Backfill integer-FK UUIDs except transaction log_uuid | Backfill primary-local FK UUIDs, excluding log targets and transaction log_uuid |
| 3 | Resolve logs.token_uuid locally | Backfill LOG_DB.logs owned UUIDs |
| 4 | Backfill transaction log_uuid locally | Backfill LOG_DB.logs user/channel/token UUIDs from primary owners |
| 5 | Ensure catch-up indexes | Backfill primary token_transactions.log_uuid from LOG_DB.logs |
| 6 | Finalizer-only unique-index promotion | Ensure catch-up indexes on each authoritative database |
| 7 | Global validation | Finalizer-only unique-index promotion on each authoritative database |
| 8 | Write primary marker | Global cross-database validation |
| 9 | Not applicable | Write log marker, then write primary marker last |

If only one split marker exists after a crash, the next finalizer reruns all
phases and global validation. Cross-database marker writes cannot be atomic, so
partial marker state is expected and recoverable. The primary marker is written
last but does not permit startup to skip the log-marker lookup.

### 6.3 Missing rows as the work queue

Use the UUID columns themselves as durable progress. A successful conditional
update removes a row from the next missing-value query, so no persistent cursor
is required.

Run NULL and empty-string passes separately:

    SELECT id, <observed reference columns>
    FROM <target>
    WHERE id > ?
      AND <uuid column> IS NULL
    ORDER BY id
    LIMIT 1000;

Repeat with <uuid column> = ''. Advance the in-memory last_id over every
examined row, including orphans and ambiguous token keys, so unresolved rows do
not pin a batch. Restarting from id zero is safe because completed values no
longer match the missing predicate.

### 6.4 Batch-local reference resolution

For integer FKs:

1. Collect positive reference IDs from the current target batch.
2. Deduplicate and sort them.
3. Query at most 400 IDs at a time from the authoritative reference database.
4. Build updates only for IDs with populated owner UUIDs.
5. Recheck target id, missing UUID, and the observed integer FK in the update.

For logs.token_uuid, deduplicate at most 400 (user_id, token_name) keys and use a
batch-local aggregate grouped by both columns. The query returns at most one row
per requested key and emits a UUID only when COUNT(*) = 1. An index beginning
with (user_id, name) must support the lookup. This prevents one ambiguous key
with many duplicate token rows from consuming O(table) application memory.

### 6.5 Bind-safe conditional updates

Use a portable bind budget of 900. Derive the update chunk size instead of
assuming 200 rows:

    rows_per_statement =
      min(configured_row_limit, floor(900 / binds_per_row))

The configured row ceiling remains 200. The current SQL shapes require three
binds per owned-UUID row, five per one-condition FK row, and seven per
token-name row, producing maximum chunks of 200, 180, and 128 rows
respectively. The builder must include fixed arguments when calculating the
final chunk. Tests assert the generated statement never exceeds the budget.

Owned updates require matching id and a still-missing UUID. FK updates also
require the observed integer FK. Token-name updates additionally require the
observed user_id and token_name. A concurrent change therefore produces zero
affected rows and is retried from the new state later.

### 6.6 Validation

Final validation is topology-wide and runs only after the writer barrier:

- every authoritative owned UUID column has zero NULL or empty values;
- every owned UUID is a canonical hyphenated UUID with version 7, is unique,
  and round-trips through the project UUID parser;
- every fillable missing FK UUID count is zero;
- every populated FK UUID equals the current live owner's UUID;
- orphaned integer references and ambiguous token names are reported but do not
  block completion when their FK UUID remains NULL;
- all required indexes exist with the expected columns, uniqueness, and valid
  state; and
- split cross-database checks use bounded target and reference batches.

Catch-up never rewrites a populated malformed or mismatched value. Validation
reports the table, column, aggregate count, and bounded example IDs without
logging row content or credentials. Operators must correct those rows before
rerunning finalization.

### 6.7 Index lifecycle

When markers are incomplete, an explicit ensureUUIDCandidateIndexes schema
phase creates or verifies every required non-unique UUID candidate index before
catch-up. Token resolution must have an index beginning with (user_id, name).
FK UUID indexes remain non-unique. Owned model tags stay free of the ordinary
index so AutoMigrate cannot recreate it after finalization.

Candidate-index creation runs in the background worker, not the
readiness-critical path. It uses concurrent PostgreSQL DDL and MySQL LOCK=NONE.
SQLite uses its bounded busy retry in the background. Failure stops the cycle,
records the error, and leaves catch-up incomplete; the worker does not fall back
to an unindexed historical scan.

Finalizer mode performs owned UUID promotion:

1. Confirm no missing, malformed, or duplicate owned UUIDs.
2. Create the unique index without dropping the ordinary index.
3. Verify index columns, uniqueness, and validity from dialect metadata.
4. Drop the known ordinary index only after verification.
5. Reread metadata after a dialect-classified duplicate-object race.
6. Return all non-duplicate DDL errors and leave markers absent.

Use PostgreSQL CREATE UNIQUE INDEX CONCURRENTLY outside a transaction. Use
MySQL online ALTER TABLE with LOCK=NONE when supported and fail for an explicit
maintenance retry when it is unavailable. Run SQLite promotion only in the
operator-approved finalizer window. Apply a bounded lock or statement timeout
on every dialect. Default lock acquisition timeout is 5 seconds and default DDL
statement timeout is 30 minutes; both remain configurable.

EXTERNAL_UUID_BACKFILL_ALLOW_BLOCKING_DDL defaults to false. If MySQL rejects
LOCK=NONE, finalization fails without fallback. An operator may set the flag
only during an approved maintenance window, after which the finalizer may retry
with the documented blocking statement. SQLite has no online DDL and no
maintenance-window concept that maps onto a single-process default deployment,
so its DDL runs under the bounded busy retry and context deadline without the
flag; the migration must complete automatically there. A retryable finalizer
failure means no marker was written, the ordinary index remains usable, and the
same v3 finalizer can be rerun after the external condition is corrected; the
synchronous finalizer mode does not loop automatically, while automatic
completion retries only after a fresh quiescence streak.

PostgreSQL retries must detect and remove an invalid same-name concurrent index
before recreating it. No dialect may accept a same-name index until metadata
proves that it is valid, unique, and covers exactly the owned UUID column.

### 6.8 Startup and writer compatibility

Add an error-returning InitDatabases(ctx) bootstrap orchestrator that initializes
both schemas before migration orchestration. The application entry point uses
this API and logs a returned terminal error once.

- Schema migration and marker lookup are synchronous.
- Master nodes start catch-up in a context-bound background worker when markers
  are absent and finalizer mode is disabled.
- Each catch-up cycle is limited to 10,000 examined target rows or 30 seconds,
  whichever occurs first.
- Active backlog is rescheduled after 5 seconds; a full no-work pass is
  rechecked after 5 minutes during the mixed-writer window.
- Finalizer mode runs synchronously and fails startup on any reconciliation,
  DDL, validation, or marker error.
- Non-master nodes never execute catch-up, DDL, validation, or marker writes.

Use EXTERNAL_UUID_BACKFILL_MAX_ROWS_PER_CYCLE (default 10000, range
1000..1000000), EXTERNAL_UUID_BACKFILL_MAX_CYCLE_DURATION (default 30s, range
1s..30m), EXTERNAL_UUID_BACKFILL_ACTIVE_INTERVAL (default 5s, range 0s..5m),
and EXTERNAL_UUID_BACKFILL_IDLE_INTERVAL (default 5m, range 5s..1h). Invalid
settings fail configuration loading. The row budget counts examined target rows
globally across roles, phases, tables, and columns in one cycle. The next target
query is reduced to the remaining budget. The duration is a context deadline,
checked by every query, update, and inter-batch transition. Application shutdown
cancels the worker through the main process context.

Use EXTERNAL_UUID_BACKFILL_LOCK_TIMEOUT (default 5s, range 1s..5m) and
EXTERNAL_UUID_BACKFILL_DDL_TIMEOUT (default 30m, range 1m..24h) for finalizer
DDL.

InitDB retains a primary-only, marker-free compatibility catch-up for existing
callers. InitLogDB completes topology initialization and may invoke the global
coordinator. The application entry point uses the new bootstrap path so normal
unified startup does not execute both compatibility paths.

Implement error-returning internal primary and log initialization helpers.
InitDatabases(ctx) calls them directly and returns errors. Legacy InitDB and
InitLogDB remain compatibility wrappers: InitDB starts a new initialization
generation, InitLogDB fails clearly if primary initialization is absent, and a
second InitLogDB call in the same generation is a no-op. The wrappers process a
terminal error once at their boundary; phase helpers never log returned errors.

The entire upgrade, backfill, and migration must run and complete automatically
on a default deployment, remaining fully backward compatible and idempotent on
both sides of completion. EXTERNAL_UUID_BACKFILL_AUTO_FINALIZE (default true)
therefore lets the background worker finalize on its own: once the configured
number of consecutive no-work passes has been observed
(EXTERNAL_UUID_BACKFILL_AUTO_FINALIZE_IDLE_PASSES, default 3, range 1..1000 —
roughly fifteen minutes of quiescence at the default idle interval), the worker
runs the same full finalizer the operator flag would run. Sustained quiescence
is the automatic stand-in for the drained mixed-writer window: it proves every
writer still running is UUID-aware. A failed automatic attempt writes no
marker, keeps the ordinary indexes usable, is reported once, and is retried
only after a fresh quiescence streak; it never takes the process down.
Completion is backward compatible because every UUID column stays nullable and
each dialect's unique index treats NULLs as distinct, so a pre-UUID writer's
inserts still succeed after promotion.

Operators who want the manual lifecycle instead may set
EXTERNAL_UUID_BACKFILL_AUTO_FINALIZE=false and enable finalizer mode only after
every active and rollback-capable writer is UUID-aware and old processes and
transactions are drained. The existing EXTERNAL_UUID_BACKFILL_FINALIZER flag
selects synchronous finalizer mode and is the operator's attestation that the
barrier evidence is complete.
The evidence records the first UUID-aware writer release commit, every active
instance version, the oldest permitted rollback version, and process and
transaction drain timestamps. IsMasterNode alone is not the writer barrier.

### 6.9 Errors, concurrency, and observability

Conditional data updates allow multiple catch-up workers. Marker and index
creation races are successful only when the database error is classified as a
duplicate object and a metadata reread verifies the exact expected object.

Every database operation receives context.Context. Migration helpers wrap and
return errors with github.com/Laisky/errors/v2. The bootstrap boundary logs the
terminal error once. Model helpers obtain their logger from context rather than
using the global logger.

Structured DEBUG or INFO events report topology, mode, phase, table, column,
examined rows, updated rows, unresolved rows, duration, and marker state. They
must not contain DSNs, credentials, token keys, UUID row values, or row content.
Emit DEBUG once per batch and INFO once per cycle or finalizer phase. Extend the
project metrics recorder with:

- oneapi_uuid_backfill_rows_total, labeled by role, phase, target, and result;
- oneapi_uuid_backfill_last_backlog, labeled by role and target;
- oneapi_uuid_backfill_cycle_duration_seconds, labeled by role, mode, and
  result; and
- oneapi_uuid_backfill_finalizer_total, labeled by role and result.

All labels come from compile-time registries. No ID, UUID, DSN, error message,
or other unbounded value is a metric label.

## 8. Prerequisites and Delivery Sequence

### 8.1 Prerequisites

Before implementation starts:

- preserve the additive UUID columns, create hooks, FK UUID writer population,
  and bind-safety work defined by the parent proposal;
- inventory every master and non-master writer version and identify the oldest
  version allowed during rollback;
- provision primary and log databases in CI and export mandatory MYSQL_DSN,
  MYSQL_LOG_DSN, PG_DSN, and PG_LOG_DSN values instead of allowing the
  acceptance matrix to skip;
- prepare a sanitized production-scale dataset or staging clone for query-plan,
  lock, heap, and duration measurements;
- provide an operator-controlled finalizer flag, one-master execution window,
  database backups, and a maintenance window for index promotion; and
- agree on release artifact storage for test logs, query plans, metrics, and
  rollout evidence.

No implementation may reuse the v2 marker keys or reinterpret them as v3.

### 8.2 Ordered delivery

1. Implement v3 markers, explicit topology, authoritative ownership, the
   coordinator, corrected phase ordering, and P0 regression tests.
2. Add the shared registry, bind-budgeted SQL, bounded token aggregation,
   consistency validation, and instrumented SQLite tests.
3. Implement index lifecycle and dialect-specific DDL, then run the live MySQL
   and PostgreSQL matrix.
4. Add background catch-up scheduling, metrics, and the operator finalizer
   lifecycle.
5. Run scale, concurrency, rollback, and release qualification before enabling
   finalization in any deployment.

No later step may be accepted while a prerequisite P0 task remains incomplete.
P0 implementation may be developed first, but P0 is not release-qualifiable
until the bind-budget, registry, validation, and index-lifecycle P1 tasks used by
the coordinator are also complete.

## 13. Definition of Done

Implementation tasks may be checked after their code and focused tests merge.
Acceptance tasks require the named evidence. Rollout tasks require evidence from
the target environment. Verification tasks and this definition control release
acceptance; they do not prevent incremental task completion.

The remediation is complete only when:

1. Every implementation, acceptance, rollout, and verification item in this
   document is checked with linked evidence.
2. Current-generation unified and split finalizer tests prove dependency-correct
   marker ordering and partial-marker recovery.
3. SQLite, MySQL, and PostgreSQL qualification jobs run without skipped backend
   suites.
4. The full scale fixture proves bounded result materialization, bind count, and
   heap rather than only final row values.
5. A staging or production-clone rollout completes the writer barrier,
   finalization, restart, and rollback rehearsal.
6. Completed UUID coordinator execution is measured as marker-only and no
   deployment relies on a v2 completion marker.
7. Compact UUID storage remains tracked separately and is not required to close
   this remediation.

### 14.4 Writer-contract finding (UUID-A22)

Only 6 of the 15 denormalized FK UUID columns are filled by a writer inside
package `model`: `users.inviter_uuid`, `tokens.user_uuid`,
`user_request_costs.user_uuid`, `mcp_tools.server_uuid`,
`passkey_credentials.user_uuid`, and `logs.user_uuid`.

The other 9 are filled only by explicit call sites outside `model`, which is the
design the parent proposal chose deliberately: a generic create hook cannot
resolve every owner without extra reads. The consequence is that the
UUID-aware-writer contract for those columns lives in call sites and cannot be
enforced by the model layer:

- `token_transactions.log_uuid`, `token_uuid`, and `user_uuid` are stamped only
  in `controller/token.go`; `CreateTokenTransaction` itself is a bare create.
- `redemptions.user_uuid` is stamped only in `controller.AddRedemption`.
- `async_task_bindings.user_uuid`, `token_uuid`, and `channel_uuid` are stamped
  by relay adaptors; `SaveAsyncTaskBinding` resolves nothing itself.
- `logs.channel_uuid` and `logs.token_uuid` depend on the caller invoking
  `SetLogExternalUUIDs`; `RecordConsumeLog` copies no UUID of its own, while
  `RecordLog` does fill `user_uuid` via `FillLogUserUUIDByID`.

This does not block the backfill: catch-up fills these rows and finalization
blocks on any that remain fillable. It does mean the writer barrier
(UUID-R02) must be verified against those call sites, not against the model
layer, and that a new producer of any of those rows can silently reintroduce a
fillable gap. `model/uuid_migration_writer_test.go` records the responsible path
for each of the 15 columns so the asymmetry is visible rather than folklore.

### 14.5 Automatic completion directive

A follow-up directive requires the entire upgrade, backfill, and migration to
run and complete automatically by default, fully backward compatible and
idempotent before and after completion. Implemented as:

- EXTERNAL_UUID_BACKFILL_AUTO_FINALIZE (default true) and
  EXTERNAL_UUID_BACKFILL_AUTO_FINALIZE_IDLE_PASSES (default 3): the background
  worker finalizes after sustained quiescence; failures are retryable and never
  affect startup. Evidence: TestMigrationCompletesAutomaticallyByDefault,
  TestAutoFinalizeBacksOffAfterBlockedValidation.
- SQLite finalization no longer requires EXTERNAL_UUID_BACKFILL_ALLOW_BLOCKING_DDL,
  which now gates only the MySQL blocking fallback. Evidence:
  TestSQLitePromotionNeedsNoOperatorFlag.
- Backward compatibility after completion is proven, not assumed: a pre-UUID
  writer's inserts (NULL uuid columns) still succeed once the unique indexes
  exist, because every dialect treats NULLs as distinct in a unique index.
  Evidence: TestOldWriterStillWorksAfterCompletion.
- Idempotence across the whole lifecycle: completed state is marker-only in
  both modes and never rewrites a populated value.

| `cycleWindowExpired` matched the `DeadlineExceeded` sentinel | A real DDL statement timeout — the retryable failure UUID-042 exists to produce — was silently reported as "the cycle ran out of time". | Match on the cycle's own context; an index-phase failure now stops the cycle and records the error. |
| The `InitDB` compatibility path could finalize | With the finalizer flag set, `InitDB` alone promoted indexes and wrote v3 markers, contradicting the marker-free contract it documents. | The compatibility path is catch-up only. |
| The query-plan fixture seeded globally unique token names | The composite index had no advantage, so the planner picked the single-column name index and the test proved nothing about UUID-037. | Token names now repeat across users, which is both realistic and the only condition under which `(user_id, name)` matters. |

### 14.6 Measured cost (PostgreSQL, single core, untuned)

Recorded from `TestExternalUUIDFinalizerScaleT27/postgres` on a 500,000-log,
50,000-token fixture. This is not UUID-A33/A39 qualification evidence — that
requires the full 1,000,000-row fixture, three repeats per dialect, on recorded
hardware — but it establishes the shape of the cost and confirms the boundedness
the design claims.

| Metric | 500,000 logs | Projected 5,000,000 |
| --- | --- | --- |
| Finalizer wall time | 4m51s | ~49 min |
| Peak Go heap | 8.1 MiB (6.1 MiB at 50,000) | ~11 MiB |
| Heap growth | 1.33x for 10x data | gate is 2x |
| Queries | 23,735 | ~237,000 |
| Max binds per statement | 900 | 900 (budget) |
| Max rows per target query | 1,000 | 1,000 (batch limit) |

Measured phase throughput: owned UUID and single-FK columns fill at roughly
10,400 column-writes per second; `logs.token_uuid` at roughly 6,000 rows per
second, because it resolves through a bounded `GROUP BY` aggregate per 400 keys.

Measured index cost at 500,000 logs: `idx_logs_uuid` 53 MB, each FK UUID index
12-14 MB, `logs` table 265 MB. The FK indexes are flattered by the fixture: it
has one user and one channel, so PostgreSQL B-tree deduplication compresses them.
Production cardinality should be budgeted closer to the owned index's ~106 bytes
per row, so roughly 2 GB of UUID indexes at 5,000,000 logs.

**Catch-up at default settings is scheduling-bound, not throughput-bound.** Each
log row is examined once per column it needs, so 5,000,000 logs is 20,000,000
examined rows, which is 2,000 cycles at the default 10,000-row budget. At the
default five-second active interval that is about 2.8 hours of waiting on top of
roughly 40 minutes of work, for about 3.4 hours total at a ~20% database duty
cycle. That is the intended trade: it is safe under production load. An operator
who needs it faster must raise `EXTERNAL_UUID_BACKFILL_MAX_ROWS_PER_CYCLE` **and**
`EXTERNAL_UUID_BACKFILL_MAX_CYCLE_DURATION` together, because the 30-second cycle
cap binds before a larger row budget can be spent, and lower
`EXTERNAL_UUID_BACKFILL_ACTIVE_INTERVAL`.

One known inefficiency, left in place deliberately: `validateOwnedUUIDColumn` runs
twice per owned table in a finalizer, once as the promotion gate (6.7 step 1) and
once in global validation (6.6). At 5,000,000 logs that is about 10,000,000 UUID
parses and two full duplicate `GROUP BY` scans rather than five million and one.
Memoizing it would weaken the final gate, which is the one that must not trust an
earlier result, so the cost is accepted rather than optimized away.
