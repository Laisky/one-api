# Sparse rate-limit capacity experiment (registered before candidate measurements)

Baseline: public PR427 production `1783b4990bbf79030452fdbe262e561d6d2b3207`, reconstructed with exact gateway SHA-256 `13a1ec75315310d1ada3f9b343d63ccb3770ffcc604d4790e92a0e0344a51f3b`.

Separate 30-second warm-up / 60-second CPU and heap diagnostic windows passed the predeclared machine-normalized gateway load and <=15% half-window throughput-drift gates. Gateway average utilization: 53.705% CPU run and 53.405% memory run on a four-core allowance, GOMAXPROCS=3. All 8,192 requests across these two runs verified. Allocation churn's largest path is bytePairMerge (30.47%). Live heap is dominated by InMemoryRateLimiter.Request: 152.59 MiB / 70.54% of 216.32 MiB sampled inuse_space. The benchmark deliberately raises global rate limits to 10,000,000; this result must not be generalized to low-limit deployments.

Hypothesis: first-use allocation proportional to configured request limit wastes live heap for sparse keys. Cap initial timestamp capacity at 16 and let the existing append grow with actual recorded history. Change only the two new-key allocations in Request and Record. Keep timestamps, acceptance/rejection, expiry boundary, key isolation, read-only PeekExceeded, dynamic limit behavior, locking and invalid-input behavior unchanged. Do not alter GC settings, quotas, tracing, accounting, tokenization or flushing.

Validate against a copied independent pre-change limiter model, expiry/dynamic-limit/zero/negative-limit boundaries, concurrent admission, and allocation/capacity tests. Prove the capacity regression test fails for unchanged baseline code. Screen with small allocation benchmarks, then independently qualify both gateway binaries and complete the existing five alternating pairs in all short/long c8/c64 cells, 40 trials / 15,360 requests. Keep all outcomes.

**Memory-specific materiality rule, fixed before measurement:** this candidate targets retained memory, not request CPU. Require >=10% median sampled RSS reduction in both long-stream cells, in >=4/5 pairs each. Keep all previous no-regression gates: short CPU/RPS <=5% regression, latency/gap must not worsen by both >10% and >5ms, RSS may not grow >10% in any cell. Additionally require no long-cell CPU or RPS regression >5%. This replaces only the CPU/RPS >=5% *benefit* requirement for this memory-only experiment, not its safety/no-regression requirements; the motivation is the user's explicit memory objective and the measured 70.54% live-heap hotspot, not a response to candidate outcomes.

If accepted, add a separate unprofiled matched-rate steady observation (one A/B pair, 30-second warmup, 60-second window, fixed offered rate chosen below measured control throughput, same request count and concurrency). This is supplementary retention/drift evidence, not five-repeat latency evidence. If rejected, preserve an unapplied patch and continue only from the unchanged baseline; do not tune GC or relax gates to rescue the result.
